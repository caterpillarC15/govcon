The conversation you're thinking of is the **OpenClaw / Sami setup** thread from late April 2026, where you were burning ~$30/hour on Opus and we dug into why. Here's what I said about the caching problem and what the solutions look like:

## The diagnosis

The core issue isn't the model — it's that ReAct-style agent loops resend the entire context on every tool call. If your run does 20 tool calls and you've got a fat system prompt plus SOUL.md / AGENTS.md / MEMORY.md loaded, you're paying for that same context 20 times. Input tokens dwarf output tokens, often 10:1 or 20:1, on agent workloads. Jensen's GTC number was that agentic tasks burn ~1000x more tokens than chat for exactly this reason.

## What Anthropic (and others) already offer

**Prompt caching** is the existing answer to your question. Anthropic exposes it via a cache_control breakpoint per request — you mark the stable portion (system prompt, tool definitions, long documents) and subsequent calls within the cache TTL pay roughly 10% of the input cost on the cached portion. Google and OpenAI have their own versions; the mechanics differ but the principle is the same — server-side keeps the KV cache warm so you don't re-pay for tokens you already sent.

In OpenClaw gateway terms, that was a config flag:


yaml
providers:
  anthropic:
    prompt_caching: true
    cache_breakpoints:
      - system_prompt
      - tools


Expected savings — 60–90% off input cost for long runs. That alone usually fixes the "why is this so expensive" question without changing models.

## What's still missing (your original frustration)

Prompt caching is per-request and has a TTL. It's not real persistent conversation memory across sessions. The ecosystem hasn't fully solved:

- **Cross-session cache persistence** — caches expire (usually 5 min, extendable to 1 hour on Anthropic), so a conversation you return to tomorrow re-pays the full cost.
- **Selective context recall** — most APIs make you send the whole history or none of it. The thing you actually want is "remember our last 50 turns but only re-inject what's relevant to this query."
- **Client-side KV cache reuse** — open-weights models (vLLM, llama.cpp) let you persist KV caches to disk and reload them. Closed APIs don't expose this.

The directions things are moving: longer cache TTLs, hierarchical/segmented caching with multiple breakpoints, and on the agent-framework side, the "Dreaming" / on-demand recall pattern we discussed — where MEMORY.md isn't pre-loaded but queried only when a turn needs it.
